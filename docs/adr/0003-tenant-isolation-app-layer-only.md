# Tenant isolation is enforced in the application layer; Postgres RLS was rolled back

Outside interactive transactions, a Prisma client extension (`tenant-extension.js`) injects the active `organizationId` from request context into `find*`, `update`, `delete`, `count`, `updateMany`, `deleteMany` and `create` on tenant-scoped models. Inside interactive transactions, and for operations the extension doesn't cover, services filter `organizationId` explicitly. Postgres Row-Level Security was built as a second, database-level layer and deliberately rolled back. RLS needs `app.current_org_id` set per transaction on the exact connection a query runs on, and request context (`AsyncLocalStorage`) was shown empirically not to survive into Prisma's `$allOperations` hook for calls made through an interactive transaction's `tx`. A proxy-based workaround fixed the first failure but exposed a second, undiagnosed one (`resolveTenant` firing twice per request). Shipping a subtly broken security layer was judged worse than shipping one well-tested layer.

## Consequences

- The RLS migrations (`20260817120000_enable_row_level_security`, `20260817120500_grant_truncate_to_app_role`) remain applied but inert: the app connects as the table owner, which bypasses RLS. Read the README's "Tenant isolation" section before trying again.
- The extension fails open: with no request-context store, it passes the query through unscoped, with no error. Because request context doesn't reach `$allOperations` for `tx` calls, every query inside `$transaction`, whether a Prisma call or `$queryRaw`, must filter `organizationId` by hand. Existing services already do this (for example `receipt-service.js:27` and every `FOR UPDATE` query). New services must too, and each one gets a tenant-isolation test that runs inside a transaction.
- `aggregate`, `groupBy`, `upsert` and `createMany` are not covered by the extension even outside transactions. Queries using them, such as aging totals, must filter `organizationId` explicitly.
- A new tenant-scoped model must be added to `TENANT_SCOPED_MODELS`, or it leaks across organizations; this already happened once with the banking models (fixed in `f2ec0ca`).

Code changes before the first deploy

Ledgerline runs on AWS almost as it is. A few things in the repo assume localhost and need adjusting. You write these yourself; each card says which file and where. The first two are real bugs once the app sits behind a load balancer.

1Tell Express it sits behind two proxies mustbackend/src/app.js

On AWS a request passes CloudFront, then the ALB, then reaches Express. The TCP connection Express sees comes from the ALB, so req.ip is the load balancer's private address for every user. rate-limit.js keys globalLimiter and authLimiter on req.ip, which means every accountant in every firm would share one bucket of 300 requests a minute and one bucket of 5 login attempts per email.

CloudFront writes the visitor's address into X-Forwarded-For, and the ALB appends CloudFront's address. Setting trust proxy to 2 tells Express to skip exactly those two hops and read the real client address.

// backend/src/app.js, directly after `const app = express();`
// CloudFront -> ALB -> this process: two proxies in front of Express.
// Without this, req.ip is the ALB's address and all users share one
// rate-limit bucket.
app.set('trust proxy', 2);

The number has to match the real hop count. If someone could reach the ALB directly, skipping CloudFront, they could forge X-Forwarded-For and pick their own IP. The ALB security group closes that door by accepting traffic only from CloudFront's managed prefix list. Use a number here, never true: true trusts every hop, and express-rate-limit warns about it for this reason.

How to check it after deploy: log req.ip once on a test request from your phone's network and confirm it shows your public IP, not a 10.0.x.x address.

2Shut down cleanly on SIGTERM mustbackend/src/index.js

Every deploy and every scale-in, ECS sends the task SIGTERM and waits up to 30 seconds before SIGKILL. Today index.js ignores the signal, so Node exits immediately and any request still in flight (say, a receipt being posted) gets a dropped connection. Postgres rolls the transaction back, so the ledger stays correct, but the user sees an error during a normal deploy.

// backend/src/index.js: keep the server handle
const server = app.listen(env.PORT, () => {
  console.log(`Server running on port ${env.PORT}`);
});

// ECS sends SIGTERM on deploy and scale-in, then SIGKILL 30s later.
// Stop taking new connections and let in-flight requests finish.
process.on('SIGTERM', () => {
  server.close(() => process.exit(0));
});

One easy-to-miss detail: the signal only reaches Node if Node is the main process in the container. Use the exec form CMD ["node", "src/index.js"] in the Dockerfile. Running through npm start puts npm in front, and npm does not reliably forward the signal.

3Add a Dockerfile for the API new filebackend/Dockerfile

ECS runs container images, so the backend needs a recipe for one. This version installs all dependencies, including dev ones, because the same image also runs prisma migrate deploy and the Prisma CLI is a devDependency. That makes the image larger. Splitting it into a slim runtime image and a migration image is a reasonable step later, when image size starts to matter.

# backend/Dockerfile (build from the repo root: docker build -f backend/Dockerfile .)
FROM node:22-slim
WORKDIR /app
COPY backend/package.json backend/package-lock.json ./
RUN npm ci
COPY backend/ ./
RUN npx prisma generate
# RDS CA bundle so Postgres TLS can be verified (see card 4)
ADD --chmod=644 https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem /app/certs/global-bundle.pem
ENV NODE_ENV=production
USER node
EXPOSE 3000
CMD ["node", "src/index.js"]

Add a backend/.dockerignore with node_modules, .env, coverage, and src/generated, so local files never get copied into the image. node:22-slim matches the Node version in CI and is glibc based, which is what the prebuilt @node-rs/argon2 binary expects. The --chmod=644 matters: files fetched by ADD from a URL are readable only by root otherwise, and the app runs as the node user.

4Encrypt the Postgres and Redis connections config onlySecrets Manager values

RDS for PostgreSQL 15 and newer rejects unencrypted connections by default (rds.force_ssl is on). ElastiCache with in-transit encryption needs the rediss:// scheme. Neither needs code; only the connection strings change, and they live in Secrets Manager, never in git.

DATABASE_URL=postgresql://USER:PASSWORD@ledgerline-prod.xxxx.ap-south-1.rds.amazonaws.com:5432/ledgerline?sslmode=verify-full&sslrootcert=/app/certs/global-bundle.pem
REDIS_URL=rediss://master.ledgerline-cache.xxxx.aps1.cache.amazonaws.com:6379
CORS_ORIGINS=https://app.ledgerline.com
NODE_ENV=production

verify-full checks both that the traffic is encrypted and that the server really is your RDS instance, using the CA bundle the Dockerfile downloaded. NODE_ENV=production also turns on the secure flag on the refresh cookie in auth.js. env.js validates all of these at boot, so a typo stops the task before it takes traffic, and the ECS deployment circuit breaker rolls back.

5Run migrations as a one-off task, and keep them backward compatible processdeploy job

Today you run npx prisma migrate deploy by hand, and CI runs it before tests. In production it runs as a one-off Fargate task, using the same image with the command overridden, before ECS rolls out new code. The task sits in the private subnet next to the API, so it can reach RDS while RDS stays off the internet.

aws ecs run-task --cluster ledgerline --launch-type FARGATE \
  --task-definition ledgerline-api \
  --overrides '{"containerOverrides":[{"name":"api","command":["npx","prisma","migrate","deploy"]}]}' \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-app-a],securityGroups=[sg-api]}'

The subtle part: during a rolling deploy, old tasks keep serving for a minute or so against the new schema. A migration that renames or drops a column the old code still reads will break those requests. Add first, ship the code that uses it, and drop the old thing in a later release.

6Leave the frontend API URL alone no changefrontend/src/lib/api-client.js

api-client.js falls back to /api/v1 when VITE_API_URL is unset. Because CloudFront serves the SPA and routes /api/* to the ALB under the same domain, that relative path already points at the right place. Setting VITE_API_URL to a separate API domain would make the requests cross-site, and the refresh cookie (sameSite: 'strict', path: '/api/v1/auth') would stop being sent.

Staging vs production

Same architecture, different sizes. Staging can drop most of the redundancy because an outage there costs you an afternoon, while one in production costs a firm its month-end close.

Billed every hour, even with zero users

  • RDS instance hours (Multi-AZ doubles them)
  • ElastiCache node hours
  • Fargate vCPU and memory hours per running task
  • ALB hours plus capacity units
  • NAT gateway hours, per gateway
  • WAF web ACL and rules, KMS customer keys, Secrets Manager secrets (monthly)

Billed by usage

  • NAT gateway data processed per GB
  • CloudFront data transfer and requests
  • CloudWatch log ingestion per GB, and storage if retention is left at forever
  • WAF requests inspected
  • S3 storage and requests (tiny for a SPA)
  • ECR image storage

Plug the production column into the AWS Pricing Calculator with region ap-south-1 for real numbers. The always-on list is what sets the floor.

The one-minute version

Ledgerline on AWS is the same app split across managed parts. The React build sits in a private S3 bucket. CloudFront serves it from the edge and also routes /api/* to a load balancer, so the SPA and the API share one domain and the strict refresh cookie keeps working. WAF filters abusive traffic at the edge.

In Mumbai, the ALB spreads API requests across two Fargate tasks in two Availability Zones. Each task is the unchanged Express app. They share one Multi-AZ Postgres 16 database, where the ledger's balancing triggers and transactions live, and one Valkey cluster for rate-limit counters. Everything with data sits in private subnets behind a chain of security groups.

Secrets come from Secrets Manager, encrypted with KMS. Logs and alarms go to CloudWatch. GitHub Actions tests every merge, then deploys with short-lived IAM credentials: image to ECR, migration task, rolling ECS update, frontend to S3, cache invalidation.

If one Availability Zone fails, the ALB, RDS, and Valkey each move to the other one. Because every ledger write is a transaction, the failover can drop requests but cannot leave a half-posted entry behind.
